# 汎用機／専用機 選択UIの提案

ユーザー要求（原文）: 「バランスとUI周りを使って、機体の構築と構築した機体で戦闘、デフォルトというかBOTの機体を汎用機っぽさを追加し、プレイヤーは汎用機と専用機両方とも使えるように、みたいな感じにしてほしいです。汎用機はシステム側で作ってあるものを使う形で」

本資料はClaudeによる解釈・設計提案（「みたいな感じ」という原文の通り、確定仕様ではなくたたき台）。対象ファイル（PlayableEntry.cs/PlayableUI.cs、場合によりContracts.Construction）はGPTが現在FEEDBACK-08で編集中のため、Claudeは直接実装せず提案のみ行う。

## 1. 現状の確認（既に satisfy している部分）

調査の結果、データ面では既に要求の核心が成立している:
- BOTの機体は`catalog.presets[i % catalog.presets.Length]`から直接取得（`PlayableEntry.BeginMatch`）。
- プレイヤーの初期デッキも同じ`catalog.presets[]`を周回コピーして生成（`DeckConstruction.CreateDefault`）。
- プレイヤーは`ApplyPreset(index)`でいつでも同じプリセットをデッキ枠へ適用できる。

つまり「汎用機はシステム側で作ってあるものを使う」は**データ的には既に実現済み**。BOTとプレイヤーの初期機体は文字通り同じプリセット群から来ている。

## 2. 足りないもの（今回のギャップ）

現状、プリセットを適用した後も`OpenPartPicker`で自由に個別装備を変更でき、「このデッキ枠は汎用機のままか、もう専用機に変わったか」という区別がUI上どこにも表示されない。ユーザーが求めているのは、この**選択と状態の明確化**だと解釈した。

## 3. 提案

### 3.1 判定ロジック（新規コード不要、既存データの比較のみ）
デッキ枠の現在の`BuildDefinition`が、いずれかの`catalog.presets[]`と（frameId＋全装備）が完全一致するかを比較する。
- 一致する → 「汎用機: <プリセットの表示名>」
- 一致しない（1箇所でも装備を変更した）→ 「専用機（カスタム機）」

この判定は既存の`BuildDefinition`/`ConstructionCatalog`データだけで完結し、新しい永続データは不要。UI表示のみの変更で済む。

### 3.2 UI動線（PlayableUI.cs）
現在のデッキ編集画面に、明確な2つの入口を用意する:
- 「汎用機を選ぶ」: 既存の`ApplyPreset`一覧をそのまま使う（システム側に既にあるものを選ぶだけ）。
- 「専用機を構築する」: 既存の`OpenPartPicker`による部位ごとのカスタマイズ（プリセットを土台にしても、ゼロから組んでも良い）。

どちらも既存の仕組みの延長であり、新しいバリデーションや制約ロジックを増やさない。プリセットを選んだ後にさらに装備を変更した場合、自動的に表示が「専用機」へ切り替わる（3.1のロジックにより自動判定、プレイヤーの明示操作は不要）。

### 3.3 プリセットの表示名（任意、BOTの「汎用機っぽさ」強化）
現在プリセットは`standard-carbine`等の技術的なIDのみで、UI上は`PartTitle()`的な簡易変換で表示されている。「汎用機っぽさ」をもう一段強めるなら、`BuildDefinition`へ任意の`displayName`フィールド（省略時はidにフォールバック、既存データへの影響ゼロ）を追加し、"汎用機 ライフル型"のような呼称を付けられるようにする。これによりBOTの機体もプレイヤー向けHUD/キルフィード等で「汎用機」として識別しやすくなる。この部分はContracts.Constructionの変更を伴うため、GPTの判断で任意実装としてよい。

### 3.4 バランス面（ユーザーの「バランスと」という言及への対応）
汎用機と専用機の間に性能差を設けるかどうかは今回明示的な指定がないため、**設けない（同一ルールで評価される既存のコスト式をそのまま使う）ことを推奨**する。汎用機＝「調整済みで手早く使える既存構成」、専用機＝「自由度の代わりに自分で調整するコスト」という位置づけであり、人為的な性能差（例: 汎用機は弱い）を追加すると「全BOTに同等のデッキ/CTを適用する」というAGENTS.mdの既存ルールと矛盾しかねない。既存のコスト/CT計算式が両者で完全に共通であることが、この提案の前提。

## 4. 実装順序案

1. （任意・低コスト）PlayableUIに「汎用機/専用機」ラベル表示を追加（3.1の判定ロジック＋表示のみ）。
2. 画面構成を5章の通り「参戦/機体制作」の専用入口へ分離する。
3. （任意・将来）BuildDefinitionへdisplayName追加、プリセットに日本語の「汎用機」呼称を付与。

いずれも既存機能の組み合わせ・表示のラベリングが中心で、新しいゲームルールを追加するものではない。GPTの判断で優先度・実装範囲を調整して構わない。

## 5. 画面構成の具体化（ユーザー追加指示: 「専用画面的な物を作り、最初は参戦/機体制作の2種から選び、機体制作で作った機体を参戦時に選択して使う」）

現状の`PlayableEntry.Awake()`は`ShowPreparation()`へ直行し、チーム選択・デッキ編集・部位構築が1画面に同居している。これを以下の3画面構成へ分離する提案。**いずれの画面も既存のロジック（ApplyPreset/OpenPartPicker/SelectPart/CyclePart/SaveProfile/BeginMatch/DeckConstruction）をそのまま呼び出すだけで、Construction/Simulation側の新規ロジックは不要**。

### 5.1 画面構成
1. **メインメニュー（新規）**: 「参戦」「機体制作」の2択のみ。`Awake()`の直行先をここに変更。
2. **機体制作（Garage、既存UIの再利用）**: 現行の`RefreshPreparation`相当の画面から「出撃する」導線を外したもの。ApplyPreset（汎用機を選ぶ）とOpenPartPicker（専用機を構築する）の両方をここに置く。4デッキ枠を自由に編集・保存（`SaveProfile`は既存のまま）。「メインメニューへ戻る」のみ、ここから直接戦闘には入らない。
3. **参戦（BattlePrep、新規・軽量）**: チーム選択＋「機体制作」で既に組んだ4デッキ枠の**読み取り専用**サマリー（3.1の汎用機/専用機ラベル込みで一覧表示、コスト/HP等の既存Statsをそのまま流用）。ここでは部位編集の入口は出さない（編集したい場合は一度「機体制作」へ戻る）。「出撃」ボタンで既存の`BeginMatch()`をそのまま呼ぶ。

### 5.2 影響範囲
- `PlayableEntry.cs`: `Awake()`の遷移先変更、新しい画面状態（例: `MenuPhase`相当のenum）の追加、各画面用のShow/Hideメソッド追加。`BeginMatch`/`ApplyPreset`/`OpenPartPicker`/`SaveProfile`等の中身は変更不要（呼び出し元が増えるだけ）。
- `PlayableUI.cs`: 新しいメインメニューパネルと参戦サマリーパネルのUI要素追加。既存の構築パネルはほぼ無改修で「機体制作」画面として再利用可能。
- Contracts/Construction/Simulationへの変更は不要。

### 5.3 懸念点・確認事項（GPTへ）
- 現状「参戦」中に死亡後デッキを切り替える`respawnDeck`選択の仕組みと、今回の「参戦前にどのデッキで最初に出るか選ぶ」動線の関係整理が必要（重複しないよう、初期出撃デッキ＝`selectedDeck`のような形で素直に繋げられるはず）。
- 「機体制作」を経ずに「参戦」だけ選んだ場合（保存済みデッキが無い初回プレイ等）は、既存の`DeckConstruction.CreateDefault`による初期デッキ（＝汎用機プリセット）がそのまま使われる想定で、詰みは発生しない。

実装順序・画面名称・細部のレイアウトはGPT判断で調整して構わない。
